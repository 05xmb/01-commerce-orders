# 题目 01 验收检查（对照题面逐项核验 Skill）

## 1. 用途

依据原始题面对最终交付版本做逐项验收：业务规则实现、异常路径、五个必须演示的完整场景、测试证据、部署结果与 Git 流程合规。防止"只完成成功主路径"或"以开发声明代替验证"。

## 2. 触发场景

- Agent 验收阶段（独立验收会话）必须调用。
- 上线前最终复核；验收后若修改过业务代码，须对本 Skill 受影响项重新执行。

## 3. 输入

| 输入 | 说明 |
| --- | --- |
| 原始题面 | 题目 01 题面 + 题集第一部分共同要求（验收会话必须实际读取，不得凭记忆） |
| 代码版本 | 待验收 commit hash【待填】 |
| 测试证据 | 单测命令及原始输出、覆盖率原始文件与报告、并发 / race 检测输出、缺陷及复测记录 |
| 部署证据 | 流水线运行记录、部署地址、版本标识、健康检查与冒烟结果 |
| Git 证据 | 仓库链接、dev/01 提交历史、meegle 编号核验输出、PR 与门禁记录 |
| 演示环境 | 服务 base URL【待填】及预置账号 |

## 4. 执行步骤

### A. 业务规则逐条核验（题面 8 条）

- **A1 下单与快照**：只能购买在售且数量足够商品；订单含下单时商品与价格快照；改价 / 下架后旧订单金额不变；可售数量反映占用。
- **A2 关闭与释放**：待付款保留时长按服务端时间；主动取消与超时关闭均释放占用；重复关闭不多释放。
- **A3 支付通知**：鉴权、订单与金额匹配；重复通知不重复记款；同一渠道交易号不属两单；金额不符 / 未知订单 / 验签失败的处理结果可查询。
- **A4 迟到支付**：关闭后成功通知不恢复订单、不重占库存，进入异常待处理列表；客服可据此发起退款。
- **A5 退款审核**：已付款未发货可申请整单退款；申请期间暂停发货；客服同意 / 拒绝均留原因；拒绝后可继续发货；退款与发货并发只有唯一合法结果。
- **A6 退款执行**：渠道确认后买家可见结果；售前退款回补库存一次；渠道失败保留待处理可重试；迟到支付退款不回补库存。
- **A7 发货**：仅合法待发货订单可发货且仅一次；已发货不受理售前退款。
- **A8 运营核查**：按订单穿透收款 / 退款 / 发货 / 异常记录；可售数量、已收款、已退款汇总正确；异常记录不能通过修改订单状态消失。

### B. 五个必须演示场景逐个核验

- **B1 正常成交**：上架 → 购买付款 → 发货 → 买家查运单 → 运营核查收款与库存。
- **B2 缺货与弃单**：20 并发下单争抢 5 件无超卖 → 部分未付款关闭 → 释放后他人购买成功。
- **B3 售前退款**：付款后申请 → 发货被限制 → 客服批准 → 首次退款失败、重试成功 → 订单与数量一致。
- **B4 迟到支付**：先关闭 → 成功通知到达 → 客服异常列表发现 → 退款 → 无重复释放与重复退款。
- **B5 操作竞争**：退款与发货并发、重复支付 / 退款通知、越权访问他人订单，均有明确且合法的结果。

### C. 通用要求核验

- **C1 持久化**：核心业务数据落库，重启后可查。
- **C2 页面**：最小可操作页面覆盖商品与订单、仓库待发货、客服退款及异常支付、运营核查。
- **C3 质量门禁**：gofmt / `go vet` / `go test -race` 通过；整体及核心包单测语句覆盖率 ≥85%（核对原始 coverage 文件，非自述）；无删测试 / 弱化断言痕迹。
- **C4 模拟渠道**：可演示成功、失败、超时、重复通知四类场景。
- **C5 Git 流程**：MCP 建仓记录、dev/01 真实过程提交（非一次性补造）、commit 格式与 meegle 核验输出、PR 门禁与合并记录。
- **C6 部署**：主分支合并版本经流水线（质量检查 → 单测 + 覆盖率门禁 → 构建 → 部署 → 健康检查 → 业务冒烟）实际部署；部署制品与发布提交一致；有可访问地址与回滚说明。
- **C7 版本一致性**：测试版本、验收版本、合并版本、部署版本的对应关系清晰；验收后改动已重验。

### D. 越权与安全抽查

- 修改请求中的用户编号不能越权；跨买家 / 跨角色访问被拒绝；仓库 / 日志 / 截图中无密钥与敏感信息。

## 5. 输出格式

输出 Markdown 验收报告：

| 字段 | 内容 |
| --- | --- |
| 验收元信息 | 时间、验收会话、代码版本、题面版本 |
| 逐项结论表 | A1~A8 / B1~B5 / C1~C7 / D，每项：通过 / 不通过 / 证据缺失 |
| 证据位置 | 每项指向具体证据（文件路径、命令输出、流水线运行 ID、部署 URL、视频时间点） |
| 缺陷清单 | 不通过项：现象、违反的题面条目、复现步骤 |
| 总结论 | 整题是否达到验收标准 |

## 6. 失败处理

- 任何"不通过"或"证据缺失"项：退回开发分支修复，重新执行受影响阶段（测试 / 验收 / 部署中受波及者），并在报告中关联前次结论形成闭环。
- 验收不得依据开发 Agent 或本工具的自述结论；无证据项一律记"证据缺失"，不得编造缺陷，也不得放行无证据项。

## 7. 完成标准

- A / B / C / D 全部条目有明确结论，且每条结论附可复现证据位置。
- 报告保存于仓库（建议 `reports/acceptance/`），并作为 PR 与最终交付清单的一部分；调用记录汇总进 `skill-usage.md`。
