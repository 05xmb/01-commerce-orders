# 订单交易一致性检查（题目 01 业务专项 Skill）

## 1. 用途

检查订单、库存、支付、退款、发货之间的业务约束是否成立，以及跨环节异常（迟到支付、并发竞争、重复通知）是否按题面规则收尾。用于发现"单个接口正确但组合起来破坏业务一致性"的问题。

## 2. 触发场景

- 开发 Agent 完成任一业务环节（下单 / 支付回调 / 退款 / 发货）后自检。
- 测试 Agent 执行完每个场景用例后核验最终数据状态。
- PR 合并前的最终一致性核查。

## 3. 输入

| 输入 | 说明 |
| --- | --- |
| 数据库访问方式 | 【待填：SQLite 文件路径 / PG 连接串，来自项目配置】 |
| 服务地址 | 【待填：本地或部署环境 base URL】 |
| 检查对象 | 全量核查，或指定订单号 / 场景名称 |
| 业务参数 | 初始库存 5、单价 10000 分、支付保留时长【待填：与教学时钟一致】 |

## 4. 执行步骤

逐项执行以下检查（可借助 SQL、接口查询、日志，逐项保留取证命令与输出）：

- **C1 库存守恒**：对每个商品核算 `可售 = 初始 − Σ待付款占用 − Σ已成交 + Σ已释放`；不存在负可售或超卖（已成交+占用 > 初始）。
- **C2 关闭幂等**：同一订单存在多次关闭 / 超时记录时，库存只释放一次；已关闭订单不再发生状态回退。
- **C3 支付幂等与鉴权**：同一订单重复成功通知只记一次款；同一渠道交易号不归属于两个订单；金额不符 / 未知订单 / 验签失败的通知均有可查询的拒绝记录，且未改变订单状态。
- **C4 迟到支付**：订单关闭后到达的成功通知全部进入异常支付待处理列表；订单未被恢复、库存未被重新占用；其对应退款完成后**未回补库存**。
- **C5 退款 / 发货互斥**：处于退款审核中的订单无发货记录；不存在"已退款订单同时存在发货记录"；已发货订单无本题的售前退款记录。
- **C6 退款幂等与回补**：同一订单重复退款成功通知只记一次退款；正常售前退款回补可售数量恰好一次；渠道失败的退款保留待处理记录且可重试。
- **C7 发货唯一**：每个订单至多一条发货记录，且仅当订单处于合法待发货状态时产生。
- **C8 异常记录独立**：异常支付 / 退款失败记录独立于订单状态存在，未被订单状态变更抹除；运营汇总（已收款、已退款、可售数量）与明细记录核对一致。
- **C9 权限与越权**：抽查越权用例结果——买家访问他人订单、非仓库角色发货、修改请求中用户编号等请求均被拒绝且有记录。
- **C10 金额口径**：所有金额字段为整数（分），无浮点；订单金额等于下单时快照，不随后续改价变化。

## 5. 输出格式

输出 Markdown 报告，包含：

| 字段 | 内容 |
| --- | --- |
| 检查元信息 | 时间、代码版本（commit hash）、数据环境、执行人 / 会话 |
| 逐项结果 | C1~C10 每项：PASS / FAIL / 不适用 + 一句话结论 |
| 证据 | 每项附取证命令（SQL / curl / 测试名）与关键输出摘录 |
| 结论 | 总体是否通过；FAIL 项清单 |

## 6. 失败处理

- 任一检查项 FAIL：报告中写明违反的题面规则编号、现场数据快照、建议修复方向，交回开发 Agent 修复。
- 修复后**重新执行全部检查项**（不只复查失败项），并在报告中关联前次失败记录，形成"发现问题 → 修正 → 复查"闭环。
- 不得为了通过检查而修改业务数据或删除失败证据。

## 7. 完成标准

- C1~C10 全部 PASS（或经学生确认标记"不适用"并给出理由），每项附可复现证据。
- 报告文件保存于仓库（建议 `reports/consistency/`），路径记入测试 / 验收材料与 `skill-usage.md`。
